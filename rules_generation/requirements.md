There are several modes, and only one is applied for one position of the chip on the line. Every bounded stretch of the line contains finitely many mode transitions. The mode transitions are given externally, not known to the generator.

A generated text provides rules for editing the right side of the chip, utilizing the same edit types defined in the "reverse_logic" module. These rules are parameterized by the chip's current position, its active mode and the state of the line. They can do mathematically continuous or discrete edits to the line. A continuous edit places elements whose position depends on the chip's position; it is updated at every step of the chip, like a drag (Example 3 of "reverse logic"). Edits by a text never change the left side of the chip, the chip's position included. An edit of a text that is refused (for example, removing something that is not on the line) is skipped, and the text keeps running.

This text is generated by a machine designed to solve optimization problems. Because it cannot perfectly solve the optimization in a single pass for every scenario, it dynamically generates a new text when it decides to. It decides when it is relevant to generate a new text and how much time it allows itself for a run, depending on its available CPU resources defined by the user. The time spent generating is outside of this system: the new text applies from the position the chip is at when the new text is installed.

When a new text is generated, all the edits made by the previous text are reversed (using the code in the "reverse_logic" module), without changing anything on the left side of the chip, the chip's position included. Rules triggering from elements behind (left of) the chip still project their consequences to the front (right of) the chip after a rollback, effectively acting as immutable constraints for the new generation. An element that straddles the chip is cut at the chip. The edits of the user that require a reversed edit are reversed too. The rules of the new text are then applied.

Example:
if the optimization problem is a simple presence ratio target for each kind of element, the rule generator finds a text of instructions that could look like this:
if the chip is between $x_1$ and $x_2$ and mode is 3, then set element A from chip to $x_3$ and element B from $x_3$ to $x_4$...
if the chip is between $x_1$ and $x_5$ and mode is 2, then set element C...
if element D exceeds a presence ratio of y when the chip is between $x_2$ and $x_6$ and mode is 1, then...
if the optimization score becomes less than $z$, then the generator runs again.
if the chip is between $x_7$ and $x_8$ and mode is 2, then the generator runs again.
...

There is a performance hyperparameter included in (0, 1). A value of 0 means the generator utilizes infinite time and CPU resources to achieve the absolute optimal score across all scenarios in one single run. A value of 1 means instantaneous generation (0 time) with re-runs every time the optimization score changes. A balanced intermediate value allows the generator reasonable time to produce a text of rules, including sparsely scheduled re-runs across scenarios.

There is a scenario that acts like a tendency, where the actual scenario will probably more or less follow it. For example, element A incites the user to switch to mode 2.
The generator should take this into account to be efficient.
